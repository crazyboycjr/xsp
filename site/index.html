xsp 1.0, scratchpads for macOS 27

One key brings it;
the same key puts it away.

xsp brings xmonad’s scratchpads to macOS: three Alacritty terminals on f1, f3 and f4. A key brings its pad up over the desktop you are on, the same key puts it away, and only one is out at a time.

Install xsp Source on GitHub

Why I created this

On Linux, xmonad gives me three scratchpad terminals on F1, F3 and F4. A key brings one up over whatever I am doing, the same key puts it away, and only one is out at a time. I use them constantly, and on the Mac I wanted exactly that: the same keys, the same behaviour, in Alacritty. The usual Mac answer is a drop-down terminal like iTerm2’s hotkey window, but that is one window that slides in, not three that come and go instantly.

The keys were the easy part. macOS 27 puts every app in the Dock and the app switcher, won’t let one app hide another app that stays out of the Dock, and shows a window on whichever desktop it was left on rather than the one you are looking at. xsp works around each of these, and uses ZeroSpace, my instant desktop switcher, to bring a pad to the current desktop. Like ZeroSpace, I built it with an AI coding agent, Claude.

If you miss xmonad’s scratchpads on a Mac, read on.

One at a time

Bringing up another pad puts the first away, as xmonad’s exclusive scratchpads do.

Here, not there

A pad comes to the desktop you are on, through ZeroSpace, rather than taking you to it.

Out of the way

No Dock icon, no place in the app switcher, and a pad steps aside when you switch apps.

Over everything

A pad covers the whole screen, menu bar included, and comes and goes without an animation.

Keys

Three pads on three keys

f1scratch-0
f3scratch-1
f4scratch-2

Each key owns one pad: Alacritty, titled after it, with your usual Alacritty configuration. The keys are Carbon hot keys, so the app in front never sees them, and xsp installs no event tap.

On an Apple keyboard the top row works the brightness and the like until you turn on “Use F1, F2, etc. keys as standard function keys” in System Settings, Keyboard; until then, hold fn with the key.

Behaviour

The way xmonad’s exclusive scratchpads behave

xsp follows xmonad’s ExclusiveScratchpads, and adds what a Mac needs, since apps there can take the focus on their own.

The first press

starts the key’s pad, and it comes up in front with the keyboard.

The same key again

puts the pad away and gives the keyboard back to the app you were in.

A pad that is away

hidden, or still out on another desktop, comes to the desktop you are on.

Another pad’s key

brings that pad up and puts the first away: only one is out at a time.

Switching apps

with cmd tab, alt tab or a click, on the same desktop, puts the pad away so the windows under it come forward.

Leaving the desktop

keeps the pad out there, ready for when you come back.

How it works

Working around macOS 27

xsp runs as a login agent with Accessibility access. Each pad is a small app of its own, Alacritty under its own bundle id, which xsp keeps in ~/Library/Application Support/xsp/, so that macOS can hide, show and focus exactly that pad.

Every app sits in the Dock

and in the app switcher.

Each pad’s app is marked as an accessory app, LSUIElement, so it has no Dock icon and no place in cmd tab. After every change, xsp registers the app again, so LaunchServices sees the mark.

One app can’t hide another’s accessory app

The ordinary call refuses.

So xsp hides a pad through Accessibility, setting kAXHidden the way cmd h does, and shows it with a LaunchServices reopen, which needs no permission. Until the permission is granted, pads stay ordinary Dock apps and hide the ordinary way.

A window shows where it was left

on its own desktop, not on yours.

The window server keeps a hidden window’s desktop, so before showing a pad, xsp asks ZeroSpace to move its window to the desktop you are on. Without ZeroSpace, showing a pad switches to the desktop it is on.

A pad covers the whole screen, menu bar included. Alacritty’s own full screen changes the menu bar’s presentation and animates it, so xsp loads a small library, xsp-overlay.dylib, into the pads alone as they start. It raises the terminal window above the menu bar, sizes it to the screen, and turns off the window’s show and hide animation, which works because the pads’ apps are signed without the hardened runtime. Built with XSP_OVERLAY=0, xsp leaves the pads as your Alacritty configuration has them.

Each pad’s app holds a copy of Alacritty itself, since a symlink would start Alacritty under its own name. xsp refreshes the copies and signs them again whenever Alacritty is updated, with the same identity as itself, so that each pad keeps the permissions you give it.

Command line

The keys, from a shell

The xsp command talks to the running agent through a Unix socket, ~/.cache/xsp.sock; the agent logs to ~/Library/Logs/xsp.log.

Toggle and look

xsp toggle 0   # what f1 does; 1 is f3, 2 is f4
xsp status     # each pad's process, windows and desktop

ZeroSpace

Instant desktop switching for macOS: cmd and a number, and that desktop is there, with no slide. xsp asks it to move a pad’s window to your desktop.

Install

Build it on your Mac

xsp needs macOS 27; it has been tested on macOS 27.0.1 on Apple Silicon. It works with Alacritty from its release, in /Applications or ~/Applications, or from nix-darwin, and with ZeroSpace running, though it does not need it. Building takes Rust and the Xcode Command Line Tools.

Build and start

git clone https://github.com/crazyboycjr/xsp
cd xsp
sh build.sh

build.sh installs ~/.local/bin/xsp and its overlay library, and starts the login agent xyz.crazyboycjr.xsp. Allow Accessibility when macOS asks, once. Alacritty anywhere else is found through XSP_ALACRITTY, set when you build.

Keep the permissions across builds

CODESIGN_IDENTITY="Local Code Signing" sh build.sh

An ad hoc signature changes with every build, and macOS then asks for the permissions again. Make a self-signed certificate in Keychain Access (Certificate Assistant, Create a Certificate, of type Code Signing) and build with its name, or put the line in signing.env beside build.sh.

xsp signs its pads with the same identity, so the login agent carries these settings too.

Stop and remove

launchctl bootout gui/$(id -u)/xyz.crazyboycjr.xsp
rm ~/Library/LaunchAgents/xyz.crazyboycjr.xsp.plist
rm ~/.local/bin/xsp ~/.local/bin/xsp-overlay.dylib
rm -r ~/Library/Application\ Support/xsp

Then take xsp out of System Settings, Privacy & Security, Accessibility.

Where the login keychain is locked, as over ssh, keep the certificate in a keychain of its own and name it with CODESIGN_KEYCHAIN, its password in CODESIGN_KEYCHAIN_PASSWORD. The agent’s plist then holds that password in plain text, readable only by you, so give the keychain nothing but the certificate.

Limits

Worth knowing first

  • xsp has only been tested on macOS 27.0.1 on Apple Silicon.
  • There are three pads, on f1, f3 and f4, set in the source; to change them, edit KEYS in src/main.rs and build again.
  • The pads are Alacritty and nothing else, and each keeps its own copy of it.
  • xsp reads the current desktop through private calls to the window server, which a macOS update can change.
  • Without ZeroSpace, a pad left out on another desktop takes you there when you show it.
  • The overlay loads a library into the pads, which needs their apps signed without the hardened runtime.
